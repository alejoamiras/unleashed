## The canary that found a bug

The runbook's step 9 names a real-origin token-list canary; the repo's testing rule (external-system data gets one `describe.skipIf(!ENV)` real-data test) says it should exist, so it was added rather than described: `TOKEN_LIST_LIVE=1` on `token-list.test.ts` — fresh load, chain filter, cache hit without a second request, never membership. First run: `fallback`. `tokens.uniswap.org` now carries 184 Solana entries (chain `501000101`, base58 addresses); `tokenListSchema` validated the WHOLE array, one foreign entry failed it, and every load in the shipped app would have degraded to the cache → manifest-only, silently. Fix: the list schema keeps only the envelope (`name`, `tokens: unknown[]`); entries are validated ONE BY ONE after the chain filter, so a foreign-chain shape is never inspected and a malformed entry on our chain is dropped, not fatal. The security posture is unchanged (byte cap while streaming, `redirect: "error"`, only the validated subset persisted, poisoned-cache rejection) — the unit tests re-pin the envelope failure and the per-entry drop.

Lesson for the skill: a validation that is stricter than the data source's contract is a liveness bug waiting for the source to grow. The list format has always been multi-chain; the entry schema belonged behind the chain filter from the start.
