## Collision / dedup risks

- Two ERC-20 ABIs (`script-l1.ts`, `useL1Usdc.ts`) → unify in bridge-core before adding a third.
- Address derivation lives in 3 places (`script-l2.ts`, `bridge-deployments.ts`, `deploy-sandbox.ts`) → ONE `derive*` module in bridge-core, keystone-pinned.
- Journal `assetKind` binary is read in ≥7 places (`deploymentMatches`, recovery-key binding, backup validation, `asset-label`, `BridgeStepper`, `BridgeJournalCard`, `BridgeForm`) — a per-token model must replace the binary in all of them, not sit beside it.
- `check-sole-consumer.sh` and `noir-artifact-classids.test.ts` are pointed at `token_bridge` — re-point, don't add a second tripwire.
- `useDeposit.characterization.test.ts` pins `deposit-flow.ts` verbatim — the any-token refactor will churn the snapshot deliberately; re-pin once, not per phase.

## Risks the plan must sequence around

1. **In-contract deploy unproven in TXE** → Phase 1 opens with a spike: minimal hub `register_token` + TXE test that publishes a Token and mints on it. If TXE can't, fall back to SDK-side deploy of the hub-derived instance (same address; hub still verifies by derivation) — the design tolerates both.
2. **CREATE2 keystone**: Solidity (`Clones.predictDeterministicAddressWithImmutableArgs`) ↔ TS (viem) ↔ Noir (hub) must agree on the exact clone initcode bytes; a mismatch strands deposits. Fixed-vector keystone across all three toolchains from day one.
3. **Register content hash** joins the 3 existing keystone vectors (Solidity/Noir/TS) — 4th vector, same tests.
4. **Toolchain**: hub compiles with the 5.0.1 nargo via `compile.sh`; TXE server `@aztec/txe@5.0.1`. No bump.
