# Recon — bun-native-tooling (an arc of the Bun 1.4 adoption)

Four read-only sweeps of the base branch: (1) every child-process call site in `packages/bridge-core/scripts`, (2) reusable spawn helpers repo-wide, (3) how those scripts are tested and invoked, (4) the Bun 1.4 process-API facts the arc relies on, checked against the installed runtime and Bun's own bundled docs/types.

## Verified facts (F) and corrected claims

- F1 `bun --version` 1.4.0; no 1.3.x binary is installed, so "new in 1.4" claims (detached forwarding, live `process.ppid`, `child.kill()` false-on-dead) cannot be A/B-verified here.
- F2 `Bun.$` is literal-by-default (Bun's bundled `shell.mdx`: no system shell; interpolated values are single literal strings; `$.escape`, `{ raw }` opt out). Its "Argument injection" section warns that a literal argument can still be a hostile FLAG to the target binary — the class this arc closes for cast/forge. `Bun.spawnSync([bin, ...args])` has no parser at all.
- F3 Types (bun-types 1.3.14 `bun.d.ts:6696-7306`, `shell.d.ts`): `SpawnOptions` has cwd, detached, env, stdio/stdin/stdout/stderr (`"pipe"|"inherit"|"ignore"|…`), onExit, signal, timeout, killSignal (default SIGTERM), maxBuffer — and **no `encoding`** (stdout/stderr are `Buffer`/`ReadableStream`). `SyncSubprocess` has `exitCode`, `success`, `signalCode?`, `exitedDueToTimeout?`, `exitedDueToMaxBuffer?` — **no `.status`**. `Subprocess.kill(): void`. `$.ShellError extends Error { stdout, stderr, exitCode }`; non-zero exits throw unless `.nothrow()`.
- F4 A corrected claim: `child.kill()` "false-on-dead" conflates Node's `ChildProcess.kill(): boolean` with Bun's `Subprocess.kill(): void`.
- F5 Semantic diffs a naïve swap would hit: `execFileSync`/`execSync` THROW on non-zero exit but `Bun.spawnSync` does not (needs `if (!res.success) throw`); five `spawnSync(...).status` sites (`verify-l1.ts:50,90`, `portal-artifact.ts:49,94`, `deploy-bridge-{mainnet:510,testnet:541}`); `encoding: "utf8"` strings become Buffers (`verify-l1.ts:78,81` rely on implicit coercion); `maxBuffer` overflow surfaces as `exitedDueToMaxBuffer` + `killSignal`, not Node's `ERR_CHILD_PROCESS_STDIO_MAXBUFFER`; `stdio` vocabulary is compatible; no bridge-core code reads fields off a caught exec error.
- F6 Bun's `node:child_process` is 🟡 partial (nodejs-compat.mdx: missing `proc.gid/uid`, `Stream`, IPC socket handles) — and these scripts ALREADY run on it under `bun`; none of the gaps is exercised.
- F7 Deploy conductors soft-fail their own verification (`deploy-bridge-{testnet:540,mainnet:509}` log ⚠ and continue on a non-zero `verify-l1.ts` exit; gated on `ETHERSCAN_API_KEY`), while `rebuildAndVerifyPortal()` at `:139`/`:153` throws. Pre-existing behaviour; preserved verbatim (an operator-facing semantics change is out of scope — pinned in the plan's Asks).
- F8 An earlier lesson: `Bun.spawnSync` blocks the event loop (deadlocked a `Bun.serve` registry) — irrelevant to these CLI scripts, which have no concurrent listener.
- F9 `run.noOrphans` semantics per Bun's current online docs (see the reuse map row); F3's type facts come from the bun-types **1.3.14** cache, not 1.4 declarations. Planning-host toolchain: forge on PATH (`~/.foundry/bin/forge`), `~/.aztec/current/internal-bin/cast` (no `current/bin/forge`) and `~/.aztec/versions/5.0.0/internal-bin/cast` both present; git 2.53.0 (`--end-of-options`, `--literal-pathspecs` verified). Both live manifests (`apps/faucet/public/{testnet,mainnet}-bridge.json`) carry `portalSource: "forked-v1"` and `l1ChainId` → `verify-l1.ts`'s legacy TokenPortal branch (`placePortalSource()`) is unreachable for every manifest on disk. `verify-l1 --dry-run` (key-free) baseline on the unmodified base branch: TestUsdc 1 source, the forked portal 89, SwapBridgeRouter 4, UniswapFuelSwap 1, exit 0.
