Three coupled changes to the L1↔L2 bridge stack, one cutover:

- **(a)** Bridge-only ERC20 deposits move onto the router's existing Permit2 witness-bound `bridge()` entrypoint; the direct approve+portal path is **deleted** (no fallback flag — user-locked).
- **(b)** Fuel-only deposits become Permit2 witness-bound — **with zero new Solidity**: `bridge()` called with `tokenPortal = FeeJuicePortal` executes the fuel-only deposit verbatim (ABI-identical `depositToAztecPublic` — see ledger L1).
- **(c)** Private claims become **recipient-committed**: `claim_private` derives the L1→L2 consumption secret from the actual recipient in-circuit, so a relayer holding the claim inputs can submit the claim *for* a user but can never redirect funds. **The real driver is the new RELAYER CAPABILITY, not closing red-team F-007** (which the report rates Low 2.6, accepted-risk — stated honestly so the irreversible-cutover decision is made on real terms; fresh-audit LOW). Forces a fresh L2 trio (token, minter proxy, bridge) + a fresh instance of the forked portal (one-shot wiring); L1 AZLO, router, swap target, pools, FeeJuicePortal all stay.

Plus: the Foundry suite gains its first fuzz tests; a minimal relayer script ships in bridge-core; the final phase is a focused red-team re-audit of the changed surface.

## Design specification

### (c) Recipient-commitment — the exact scheme

New Noir lib `contracts/bridge/aztec/claim_secret/src/lib.nr` (path-dep'd by `token_bridge` and `keystone`, precedent `token_bridge/Nargo.toml:7`):

```noir
/// poseidon2_hash_bytes as u32 — pinned
/// literal; the TS keystone re-derives it from the string and asserts equality, and asserts
/// it differs from the FPC fuel separator (3952304070) and the protocol SECRET_HASH (4199652938).
pub global DOM_SEP__TOKEN_BRIDGE_PRIVATE_CLAIM_SECRET: u32 = 3140354885;

pub fn derive_claim_secret(claim_salt: Field, recipient: AztecAddress) -> Field {
    poseidon2_hash_with_separator([claim_salt, recipient.to_field()], DOM_SEP__TOKEN_BRIDGE_PRIVATE_CLAIM_SECRET as Field)
}
```

`token_bridge/src/main.nr` — `claim_private` (current `:104-122`) becomes:

```noir
fn claim_private(recipient: AztecAddress, amount: u128, claim_salt: Field, message_leaf_index: Field) {
    self.enqueue_self._assert_not_paused();
    assert(amount > 0, "Amount must be greater than zero");
    assert(!recipient.is_zero(), "Recipient cannot be zero");         // NEW (strand-to-unspendable edge)
    let config = self.storage.config.read();
    let content_hash = get_mint_to_private_content_hash(amount);       // UNCHANGED
    let secret = derive_claim_secret(claim_salt, recipient);           // NEW: in-circuit derivation
    self.context.consume_l1_to_l2_message(content_hash, secret, config.portal, message_leaf_index);
    self.call(TokenMinterProxy::at(config.token_minter_proxy).mint_to_private(recipient, amount));
}
```

The raw-secret parameter is REMOVED (renamed + re-semanticized, same arity/types); no other entrypoint in the contract consumes `mint_to_private` content (the contract has exactly two `consume_l1_to_l2_message` sites, one per claim). `claim_public`, both exits, pause, ownership: untouched.

TS counterpart `packages/bridge-core/src/claim-secret.ts` (sibling of `private-fuel.ts`, same pinned-literal-never-computed-at-import discipline): `DOM_SEP__TOKEN_BRIDGE_PRIVATE_CLAIM_SECRET = 3140354885`, `deriveTokenClaimSecret(salt, recipient)`, `tokenClaimSecretHash(salt, recipient)`.

Flow: deposit draws `claim_salt = Fr.random()` → `secretHash = computeSecretHash(deriveTokenClaimSecret(salt, recipient))` → sealed envelope gains `salt` (existing optional field) BEFORE the irreversible L1 tx → Permit2 witness (`tokenSecretHash = secretHash`) → `router.bridge()`. **The deposit code refuses to build a private deposit unless the active manifest declares `privateClaimMode: "salt-v2"`** (the L9 runtime interlock — a derived-secret deposit against an old bearer-bridge manifest fails closed instead of stranding). Claim (self or relayer): `claim_private(recipient, amount, salt, leafIndex)`. **Client fail-closed assert at claim time**: re-derive and check `computeSecretHash(derived) === rec.secretHashHex` before sending. The **fueled private token leg uses the same derivation**: `runSwapBridge`'s params gain a required `tokenClaimSalt` when `isPrivate` (F-005-style fail-closed throw when absent — a `Fr.random()` token secret would strand the deposit against the new `claim_private`); the fuel leg keeps its separate FPC derivation with its own salt.

**Soundness**: the L1 message commits `secretHash = H(poseidon2_ds([salt, R]))`; consumption requires the unique preimage; the message's L2 actor is the new bridge (init-once), the protocol only lets the addressed contract consume its own messages, and the new bridge's only consumer of `mint_to_private` content derives the secret from its `recipient` argument — so any successful consumption mints to an `R'` with `poseidon2_ds([salt', R']) = secret`, a targeted second preimage for `R' ≠ R`. Rests on: (A1) poseidon2 collision/second-preimage resistance AND `computeSecretHash` (the outer poseidon2-based hash the message actually commits to) second-preimage resistance — Leg C confirmed the binding is preimage-resistant (~2^254), attacker controls both `salt'` and `R'` but must still hit a fixed target; (A2) no bearer entrypoint exists or is ever reintroduced (documented invariant + Phase 2 sole-consumer static check + Phase 9 audit — Leg C verified exactly two `consume_l1_to_l2_message` sites today); (A3) protocol message addressing; (A4) domain separation (≠-asserts in keystone); (A5) client derivation correctness at deposit time (keystone vectors + claim-time assert + sandbox smoke + live canary gate). Client MUST bind `recipient` = the connected wallet: post-(c) the recipient is fixed at DEPOSIT time, so a wrong/unspendable recipient strands PERMANENTLY (no claim-time correction, unlike today — fresh-audit LOW). **The security does NOT come from secret secrecy** — the relayer can compute the derived secret; it has nowhere to spend it that redirects funds. It **cannot redirect, self-claim, or steal**. It CAN (fresh-audit HIGH-1): (i) consume the message early, nullifying it — which kills the user's self-claim path and, IF I4 holds (third-party mints need `registerSender` to be discovered), leaves the mint in a note the recipient can't find until they register the relayer — a withholding/support lever, recoverable but not "cannot ransom" as an earlier draft overstated; (ii) deanonymize — it learns `recipient↔amount↔leaf` and, if shared across users, links their L1 addresses to leaves. Both are inherent to delegating a claim; the derivation guarantees only no-theft, and the mitigation is "trusted relayer or none" (Phase 8 docs; malicious-relayer griefing is in T1).

## Fuzz strategy (five targets; exclusions are decisions, not omissions)

`contracts/bridge/evm/test/SwapBridgeRouterFuzz.t.sol`, mock-based (fork stays deterministic):
1. **`test_fuzz_witnessTamperChangesHash`** — mutate exactly one of the 12 `BridgeWitness` fields; hash must change. The witness IS the security boundary; a field that hashes-but-doesn't-bind is invisible to fixed-vector pins.
2. **`test_fuzz_bridgeAccounting`** — `bridge()` over amount ∈ [1, 2^128]: portal receives exactly `amount`, zero token/allowance residue, `Bridge` event echoes inputs; zero-amount/zero-portal revert. This entrypoint goes from dormant to carrying 100% of bridge-only + fuel-only volume; residue = owner-sweepable = the theft-shaped failure.
3. **`test_fuzz_fuelSplit`** — `bridgeWithFuel` valid domain (0 < fuel < total): exact slicing, zero residue; invalid domain reverts. Integer edges (fuel = total-1, total = 1) currently covered at two hand-picked points only.
4. **`test_fuzz_hostileSwapConsumption`** — parameterized hostile swap (pulls `consumed`, returns `returned`, transfers `transferred`): succeeds iff `consumed == fuelAmount && returned >= minFuelOutput && transferred >= returned`. Generalizes `MaliciousPrefundSwap` to the full behavior lattice of the owner-replaceable target.
5. **`test_fuzz_hostilePortal`** (codex cond. 4 / finding 8) — `bridge()` with a parameterized hostile `tokenPortal` that returns success without pulling, pulls to an attacker via the router's `forceApprove`, or returns a fake `(key, index)`. Asserts: an honest portal leaves zero router residue and emits a truthful `Bridge` event; the arbitrary-`tokenPortal` call is the newly-hot trust boundary, so the official flow's manifest-pinning is what protects users (the on-chain call itself trusts the caller-named portal — this is the phishing surface, made explicit).

Excluded deliberately: content hashes + claim-secret derivation (cross-toolchain byte-equality pins — a property no single-runner fuzzer expresses); `_hashRoute` injectivity (solc ABI-encoding's contract); Noir TXE fuzzing (no TXE harness in repo; the sandbox smoke + live canary exercise the real circuit against real messages — stronger evidence for the strand risk in question).

## Security & Adversarial Considerations

**Threat model.** (T1) malicious relayer holding `(salt, recipient, amount, leaf)`; (T2) observer of L1 calldata/mempool; (T3) hostile dApp getting a Permit2 witness signed; (T4) router owner (hot EOA — residue + `setSwapTarget`); (T5) L1 MEV/front-runner; (T6) future maintainer reintroducing a bearer entrypoint. Surfaces: Permit2 signatures, router entrypoints, the L1→L2 message/secret scheme, L2 claims, client persistence, cutover config.

- **Bearer-signature intent theft (T3 — fresh-audit HIGH-2, distinct axis)**: a user phished into signing a VALID `BridgeWitness` naming the ATTACKER's `aztecRecipient`/`tokenSecretHash` → the router faithfully bridges the user's tokens to the attacker's L2 account. Witness binding proves integrity (the tx matches the signature), NOT intent (that the signature was for the user). This is a NEW vector vs today's bridge-only path (approve + `depositToAztecPublic` pulls from `msg.sender` — no bearer signature exists), and AZLO's max-Permit2 pre-approval (`MintableERC20.sol:47-50`, red-team INFO-1) removes the approve gate, so ONE blind `signTypedData` drains AZLO. The new one-time `approve(Permit2, max)` for fuel-only likewise makes the canonical fee asset standing-Permit2-drainable. Testnet-valueless → accepted (A-1), but stated plainly and a **HARD blocker for any value-token port** (INFO-1 carried into the Phase 8 docs).
- **Generic-router portal phishing (T3 — codex cond. 4, HIGH)**: `bridge()` accepts an arbitrary `tokenPortal` and the router `forceApprove`s it before calling (`SwapBridgeRouter.sol:220-227`, `:271`), so a malicious portal named in the witness can `transferFrom` the just-pulled tokens. This is intent-phishing, NOT a calldata-integrity break: witness binding proves the tx matches what was signed, but a user phished into signing a witness that names a hostile portal loses the signed amount — exactly as they would signing any malicious approval. Mitigations: the official faucet hard-pins `tokenPortal`/`bridgeToken`/`router`/`permit2` from the manifest (client-pin test, Phase 5); `test_fuzz_hostilePortal` (Phase 1); documented worst case. The only *on-chain* mitigation is a hardwired/allowlisted portal — noted as a future-router item, out of scope here (the old direct-portal path had the identical trust shape). A-1 accepts this for testnet.
- **Witness tampering (T1/T5)**: every executed field is witness-bound and re-derived from calldata by the router; Permit2 verifies. Fork tamper legs per entrypoint; fuzz target 1. A relayed signed payload executes verbatim or not at all. (Distinct from phishing above: this is integrity, that is intent.)
- **Replay/reuse (T1/T5)**: Permit2 nonce bitmap (fork-tested), deadline, domain binds chainId+Permit2, spender binds router. Cross-entrypoint: witness spaces disjoint on `fuelAmount`. Fuel/bridge aliasing (L1 ledger): identical execution, no privilege delta.
- **Front-running claims (T2/T5)**: public — bound recipient (unchanged). Private — after (c), a leaked salt only triggers the mint to the bound recipient: the bearer window closes by construction. The salt downgrades to linkage-secret + liveness-key.
- **Cross-protocol secret reuse (T1/T6)**: three separators, ≠-asserted in keystone. A salt accidentally reused across fuel and token deposits yields different secrets.
- **Reorg (L1)**: leaf index read from mined receipts (never simulated); a reorg invalidating the index is re-extractable from the canonical chain via the persisted `depositTxHash`; claim retry tolerates not-ready. Unchanged surface from today; Sepolia-depth reorgs accepted (testnet).
- **Least privilege**: no new privileged roles; router owner unchanged (`Ownable2Step`; residue fuzz-asserted zero on the newly-hot path); new L2 trio reproduces the F-002 posture (owner has zero standing authority post-wiring); relayer holds no privilege — that is the feature; deploy key = testnet-only funds.
- **Input validation**: router — amount/portal/fuel-domain requires (fuzz-covered); L2 — amount > 0, `!recipient.is_zero()`, pause, protocol message membership + nullifier; client — fail-closed: Permit2 allowance read-backs, fuel `routerIsPrivate===false` (the WITNESS field, NOT record `isPrivate` — see the (b) guard note), claim-time re-derivation, FPC pin (existing), fuel floor (existing); deploy — per-step read-backs + candidate-never-live discipline.
- **T6 regression**: sole-consumer invariant documented at the entrypoint, Phase 9 audit check, structurally visible (any new `consume_l1_to_l2_message` call site is a one-file diff).
- **Cryptography**: poseidon2 via `@aztec/foundation` (pinned 5.0.0-rc.2) and aztec-nr's `poseidon2_hash_with_separator` — battle-tested protocol primitives; nothing hand-rolled. The 32-bit domain separator is a **namespace tag, not a cryptographic boundary** (the field hash provides the security); the exact-string re-derivation test keeps it honest (codex finding 10). Supply chain: zero new npm deps; canonical deployed Permit2. **Noir git-tag deps are not a cryptographic pin** (no `Nargo.lock` — codex finding 7): the Phase 2 artifact-diff + compile-provenance check catches drift post-compile but not provenance; committing a Noir lockfile / pinning by rev is recorded as a follow-up (deferred like F-003, not silently accepted).
