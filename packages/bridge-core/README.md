# @unleashed/bridge-core

Framework-agnostic L1↔L2 bridge logic for the Unleashed tools app — pure TypeScript over `viem` (L1)
+ `aztec.js` (L2). No React, no Vue, no server. The tools app's composables and the deploy/smoke
scripts drive these functions; the proven reference for every flow is
`scripts/deploy-sandbox.ts --smoke`.

One **generation** per network: an L1 `PortalFactory` (one storage-less portal clone per ERC-20) +
`SwapBridgeRouter` and one L2 `TokenBridgeHub` that registers a token from the factory's attested
words and derives its L2 `Token`. Every DERIVABLE address (portal, hub, L2 token) is a pure function
of that tuple and this package re-derives it rather than trusting a file; the factory, router and swap
target are deployed addresses the verifier cross-reads instead.

## File map (`src/`)

| File | Purpose |
|---|---|
| `manifest-v2.ts` | STRICT zod schema for the generation manifest (`schema: 2`; `bridge: null` = a placeholder network). Every derivable address (portal, hub, L2 token) is re-derived on parse; a manifest that disagrees with itself is rejected. The additive deposit-router fields (`depositRouter`, `fuelSwapper`, `fuel`, `legacyRouters`, `routing`) are refined against each other and the network. |
| `send-generation.ts` / `send-flow.ts` | What a send binds to (read off a manifest) and the L1 leg for every intent — token, token+gas, gas-only — through the router: `runSend` signs the Permit2 witness, sends `bridge`/`bridgeWithFuel`, and `readSendReceiptLeaves` reads the leaf indices from the mined router events (filtered to THIS router). The portal is never taken from a caller. |
| `hub-l2.ts` | The L2 leg: `claimViaHub` (register-if-first, decided at claim time by `token_for`, race-tolerant), `exitViaHub` / `preflightHubExit` / `hubExitsPaused` (fail-closed) for L2→L1. |
| `hub-token.ts` / `portal-address.ts` | The L2 token the hub derives for an ERC-20 (aztec-standards `Token`, `deployer = hub`, `salt = erc20`) and the portal clone the factory derives (`Clones.cloneDeterministicWithImmutableArgs`, salt = token). Both pinned against the on-chain derivations. |
| `register-hash.ts` / `claim-secret.ts` / `content-hash.ts` | The three-toolchain keystones (Solidity ↔ Noir ↔ TS): the factory's `register` message, the recipient-committed private-claim secret, the deposit/withdraw content hashes. |
| `factory-abi.ts` / `router-abi.ts` / `factory-registry.ts` / `erc20.ts` | Hand-written browser ABIs pinned against the forge artifacts; the factory's frozen registration + the hub's registration view read together; gas-capped ERC-20 metadata reads decoded from the factory's own bytes. |
| `l1.ts` | Permit2 `BridgeWitness` typed-data + `hashRoute`/`hashBridgeWitness`, cross-pinned to `SwapBridgeRouter`, and the `DepositWitness` `DepositRouter.hashWitness` checks (it commits to `keccak256(swapData)`), pinned to the Solidity vector in `l1.test.ts`. |
| `lifi-addresses.ts` / `lifi-abi.ts` / `across-v4.ts` / `stargate.ts` / `lifi-gas.ts` | The third-party contracts a cross-chain route touches per chain, with their runtime code hashes; the LI.FI swap/bridge ABIs; our own testnet Across V4 builder; Stargate V2 ABIs, the LayerZero options and OFT compose decoders, the fee ceiling; the fork-pinned gas budgets, `LIFI_INTEGRATOR` and the venue allow-list. |

## Key invariants

- **Leaf indices from the mined events, never a preflight simulate** (`send-flow.ts`). A concurrent deposit changes a simulated index, so the claim would retry against the wrong leaf forever. `readSendReceiptLeaves` reads them from the router's own `Bridge`/`BridgeWithFuel` events — filtered by emitter, so a look-alike event from another contract in the same receipt cannot forge them.
- **The portal is derived, never supplied.** `sendPortalFor` computes the factory's CREATE2 clone (or the canonical `FeeJuicePortal` for direct gas) and the router re-derives and refuses anything else on chain; a first send creates the clone inside the same transaction.
- **A claim is decided at claim time** (`hub-l2.ts`): `token_for == 0` ⇒ this claim also registers (one tx for public; `register_token` first for private). If another claimant registers in between, the registration path fails on the consumed register leaf and the claim is retried as a plain one — a deposit is never stranded on a race.
- **A private first claim's two transactions pay from the same bridged Fee Juice, and nothing is ever sponsored** (`hub-l2.ts` seams `registerFee` / `registeredClaimFee`): the registration spends the fuel message (`PrivateFPC.mint_and_pay_fee`, sized with `PRIVATE_HUB_REGISTER_GAS`), which leaves `amount − max_gas_cost` as the claimer's private credit at the FPC, and the claim that follows pays from that credit (`pay_fee`, sized with `PRIVATE_HUB_CLAIM_GAS`). The FPC keeps each transaction's committed ceiling, not its charge, so a first-time private bridge must carry both ceilings. The claim is sent only once its own simulation passes in the claimer's wallet: the registration's binding lands on the node first, and `claim_private` reads it at the wallet's synced block, which lags (`registrationWait`, 5 s polls, 3-minute deadline; `onRegistered` hands the caller the registration's hash as soon as it exists).
- **Secrets persisted before the irreversible L1 tx.** A lost claim salt/secret strands funds — the journal record (with its sealed fuel salt for every private fueled shape) is written before the signature is requested. **A PRIVATE claim is recipient-committed.** The stored `secret` for a private deposit is a per-deposit `claim_salt`; `claim_private` re-derives the consumption secret from `(claim_salt, recipient)` in-circuit (`deriveTokenClaimSecret` ↔ the Noir `claim_secret` lib, keystone-pinned), so a leaked salt only lets someone claim to the ORIGINALLY-BOUND recipient — a relayer can finish the deposit, never redirect it. Integrators MUST still seal the salt at rest and NEVER log/URL/plaintext-persist it: losing it strands the deposit (sole recovery input), and leaking it reveals the recipient↔amount↔leaf linkage. **Two salt rules, distinct risks:** (1) *keep it secret* — a LEAKED salt → the linkage above; (2) *keep it full-entropy-random* (`Fr.random()`, never deterministic) — the private deposit's `secret_hash` is written to L1 in the clear and the amount is public, so a WEAK salt lets an observer brute-force `(salt, recipient)` and de-anonymize the recipient pre-claim with no leak at all. Pinned by `claim-secret.test.ts`. The **public** path stays a raw secret (`claim_public` binds the recipient in its content hash).
- **The Permit2 witness is cross-pinned.** `l1.ts`'s `BridgeWitness` member list + `BRIDGE_WITNESS_TYPE` must stay byte-identical to `SwapBridgeRouter._hashBridgeWitness`. `l1.test.ts` pins the hashes; the evm fork test proves a post-signature tamper reverts.
- **Gas-share math is integer-only with two exact ceilings** (`gas-share.ts`): the slice sized from `fjPerTx` and the floor signed from it never lose a base unit to a folded division — a property test pins it.
- **Token behaviours are bounded on chain, not trusted off chain.** The clone refuses fee-on-transfer (exact-in), `amount > uint128.max`, and protects the reserve on withdraw with an exact portal-debit; a routeless token is refused before signing (`route-discovery.ts`); rebasing tokens are unsupported and surfaced as a caution, never detected.
- **Tests run under vitest, not `bun:test`.** `@aztec-labs/foundation` calls `expect.addEqualityTesters` at import, which `bun:test`'s `expect` lacks — any test that (transitively) imports `Fr`/`AztecAddress` throws at import. Always `import { … } from "vitest"`. (The vitest suite executes on the Bun *runtime* — `bun --bun vitest run` — which is a different thing.)
- **Scripts spawn other programs ONLY through `scripts/run.ts`** — argv arrays, never a shell string (`run(bin, args)` throws `RunError` on any failure; `resolveBin` finds `forge`/`cast` by one rule: `FORGE_BIN`/`CAST_BIN` override, then PATH or the Aztec toolchain folders). Argv closes shell injection, not a hostile flag: values that reach `git`/`forge`/`cast` are validated first.
- **The conductor's journal is the recovery.** Every irreversible deploy step is appended after its receipt, stamped with the chain/rollup/deployer identity; a re-run skips journalled steps and never re-derives the factory or hub. Both are additionally adopted from chain when they landed before their line was written (the two with cross-bindings); the swap target, router and pool seeds are not — a crash between landing and the append re-sends that one step, so read the journal against the chain before re-running. Never edit it, and never delete it while its generation may still be resumed: a completed generation's journal is retired, in its own commit, when the next generation starts on the same network (`bridge-generation`).
